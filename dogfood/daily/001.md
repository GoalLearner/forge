## Most important friction

**`edit_file` failed to match on a CRLF file and forced a whole-file
`write_file` rewrite.**

`lib/economy.test.js` is 222 CRLF lines with `core.autocrlf=true`. Forge's first
`edit_file` returned *"old_string was not found"*, after which it re-read from
line 193 and attempted a PowerShell byte-level hex dump — a diagnostic that
implies it suspected an encoding or line-ending mismatch — before falling back
to rewriting the entire file.

It recovered, and on a 199-line test file a full rewrite is harmless. On this
repository's 62,592-line `app.js` it would not be: a whole-file rewrite there
would be expensive and risky. This is the one observed issue that would
meaningfully limit Forge on the owner's main source file.

---

## Recommended next action

**Investigate `edit_file` line-ending normalization**, then continue daily
dogfooding.

This is not a roadmap feature — it is the concrete friction this run surfaced,
it is narrow, and it is the difference between Forge being able to edit
`app.js` surgically or not at all. Confirm whether `edit_file` normalizes CRLF
when matching `old_string`, and whether `read_file` hands the model content
whose bytes differ from what the matcher expects.

Everything else behaved correctly: discovery, verification, cost accounting,
tool selection, permission gating and repository isolation all held.
